A · Identity & selection

Which IDs the UI navigates and selects by.

D1 · Attempt identity

settled by code

What the code does

Attempt.id / AttemptModel.id is the identity round-tripped by repository conversion. The competing AttemptRecord dataclass (claims a globally unique attempt_id) is dead: not exported, not referenced by conversion, no table. (task_id, attempt_num) has no uniqueness constraint; cost records key on an execution tuple, not attempt id.

Decision

Confirm attempts.id as canonical attempt identity. No migration.

Recommendation

Confirm. Follow-up (small): delete or deprecate the AttemptRecord dataclass; optionally add a uniqueness constraint on (task_id, attempt_num).

Sources: 01-domain-persistence (DP-ENT-attempt, DP-ENT-attempt-record), 08-domain-synthesis §1. Was Q-1.

D2 · Legacy tasks vs graph nodes: joined or distinct?

decide

What the code does

A graph node is not a task row. task_region_id is an optional string — no foreign key, no proven join to task identity. Graph and legacy vocabularies (node/record/lease vs task/attempt) are separate throughout. Three reports independently recommend keeping them distinct until a conversion contract is evidenced.

Decision

Does the UI ever join a legacy task to a graph node, or does each mode keep its own identity space and screens?

Recommendation

Keep modes distinct. Graph is the default carrier, legacy is opt-out — the UI shows graph runs in graph terms and legacy runs in legacy terms, and treats task_region_id as an opaque informational string. No conversion layer. Revisit only if a concrete screen needs the join.

Sources: 01 §2, 02 §1–2, 03 decision 4, 08 §2. Was Q-2.

D3 · One canonical selection identity per route

decide

What the code does

The current UI selects and deep-links by a mix of identities across routes (run, task, node, attempt, decision, review), with no stated rule for which is canonical where.

Decision

Fix the identity each route selects by, so URLs, selection restore, and cross-links are stable.

Recommendation

Per-mode, per-level: run.id → route root; legacy detail by task.id (attempt via ordinal within task); graph detail by node_id scoped to run. No cross-mode canonicalisation (see D2). Write this into the view contract when screens are designed — the decision here is just "one identity per route, chosen from the persisted IDs above".

Sources: 06-ui-projections §2.

B · Authority & attribution

Who acted, and what the UI may claim about it.

D4 · Single-operator: actor strings are labels, not identity

decide

What the code does

Optional JWT auth: disabled by default; when enabled, any valid token grants everything — claims are validated then discarded. No endpoint checks role, scope, or ownership. Five incompatible attribution mechanisms record actors: fixed "user" (clarifications), deps.get_current_user (approve/reject), caller-supplied approved_by (step approval), caller-supplied decider (graph decisions), fixed "human-operator" (graph patch/requeue). None is bound to authentication.

Decision

Declare the system single-operator by design, or commission per-action authorization.

Recommendation

Declare single-operator. Consequences for the UI: render actor strings as provenance-of-record ("recorded as approved_by: X"), never as authenticated identity; build no permission-gated UI. Optional cleanup, not blocking: collapse the five attribution mechanisms to one convention.

Sources: 04 authority table (api-authn-jwt, api-authz-roles, api-identity-attribution), 09 §4. Was Q-5, minus the invented RBAC mandate.

D5 · CLI bypasses the signal queue — allowed or not?

decide

What the code does

REST POST /runs/{id}/start enqueues RUN_START and returns 202 before the transition applies. CLI runs start calls WorkflowService.apply_start_run directly and commits synchronously — bypassing the queue AGENTS.md says all lifecycle transitions use. Most other CLI lifecycle commands are REST wrappers (and don't pass a Bearer token, so they fail against an auth-enabled server).

Decision

Is CLI direct application a documented local-operator compatibility path, or must CLI conform to the queue?

Recommendation

Document it as a local-operator compatibility path for now (changing it is product work, not documentation work). Either way the UI binds to REST semantics only: 202 = accepted, not applied — which feeds D7.

Sources: 03 CON-WF-02, 04 action-run-start. Fed Q-5's uncertainty list.

D6 · Stopping-row cancel: two surfaces disagree

cheap fix

What the code does

The REST cancellation route rejects a run in STOPPING, but the workflow audit permits an applied stopping→cancelled transition. One inconsistency, low stakes, but the UI can't know whether to offer Cancel on a stopping run.

Decision

Pick one: REST rejection is correct (stopping runs can't be cancelled), or the domain transition is correct (they can).

Recommendation

Keep the REST rejection — a stopping run is already on its way to a terminal state, and a second cancel is noise. Align the workflow-side transition (or document it as the internal sweep path only). UI: disable Cancel while stopping.

Sources: 09 §3, 03 state tables.

C · State, feedback & honesty

What the UI may claim about state and freshness.

D7 · SQL is the write authority; AGENTS.md is wrong

settled by code

What the code does

SqliteEventStore.append commits events_v2 plus projections in one transaction; JSONL is a post-commit secondary sink; drain_committed_events_to_journal treats the event table as authoritative after a JSONL failure. JSONL is the source only in empty-database bootstrap. AGENTS.md says the opposite (JSONL-first). Durability tests already exist and pass.

Decision

Confirm SQL-event-first as the canonical statement.

Recommendation

Confirm. Only action: fix the AGENTS.md wording (and its stale queued status example — the enum says draft). No implementation or test work. Raised by four reports; it is one paragraph of editing.

Sources: 03 CON-WF-01 and uncertainty 6, 01 §4, 02 §4, 08 §3. Was Q-3 (and half of Q-4).

D8 · Action feedback: is "accepted + watch events" enough?

decide

What the code does

Mutating routes return acceptance (202) or the current read model — not proof of the resulting state. There is no typed queued-command outcome record proving accepted / rejected-stale / resulting state / next activity. A crash window can even apply a transition without its SignalProcessed marker (CON-WF-03). The UI today infers results by watching projections and WebSocket events.

Decision

Accept "202 + observe projections" as the v1 action-feedback contract, or require a typed command-outcome record from the backend first?

Recommendation

Accept 202-plus-observation for v1 — single operator, WS events arrive fast, and this unblocks UI work now. UI rule: after any action, show "accepted, applying…" until the projection confirms; never render optimistic success. Typed outcome record becomes a backend backlog item that would later upgrade the same UI states.

Sources: 03 decision 3 + CON-WF-03, 06 §5.

D9 · "Live" badge overstates; derived numbers unlabeled

cheap fix

What the code does

The UI's Live indicator reflects socket connectivity, not freshness of every visible projection. Frontend-computed values (stuck-run detection, token/cost/trace arithmetic, task ranges) are presented with the same visual weight as persisted facts.

Decision

Narrow Live to what it measures, and mark frontend-derived values as estimates?

Recommendation

Yes to both. Live = "event stream connected" (tooltip says so). Derived values get an estimate marker (≈) or muted styling with provenance on hover. This is a rendering convention, decidable now, no backend work.

Sources: 06 §1, §4.

D10 · Cost honesty: unpriced ≠ zero; rollup is graph-scoped

cheap fix

What the code does

Cost rollup coverage is solid for graph-mode executions only; legacy and exception-terminated executions are incompletely covered. Run-level estimated cost can conflate explicit zero, unpriced, and approximate. rate_missing == false proves a price matched, not that every billable category had a rate.

Decision

Adopt the three honesty rules for any cost display?

Recommendation

Adopt: (1) cost totals labeled with their coverage scope ("graph executions"); (2) unpriced shown as unknown, never €0; (3) estimates visually distinct from measured spend. Pure display policy; decide once, apply everywhere.

Sources: 05 §3, §4, §7.

D11 · Known evidence gaps stay gaps until implemented

settled by code

What the code does

No implementation exists for: health class, prompt pressure, repeated-work/churn detection, evidence convergence, retry information delta, causal gap, budget pace, comparable cohorts, exact prompt delivery accounting, complete transcript coverage, or node-exclusive file causality (file state is "observed at node callback", not "caused by node"). The JTBD documents demand them; the code does not provide them.

Decision

Acknowledge these as gaps the v1 UI must not fake.

Recommendation

Acknowledge. Design consequence: v1 screens are built from what exists (states, events, costs, artifacts, decisions) and leave explicit room for these rather than approximating them with lookalike numbers. Each gap becomes a candidate backend feature ticket ranked by UI value — that ranking is a design-phase activity.

Sources: 05 closing note, 07 §1, 10 §3.

D12 · Docs claim locking the code doesn't have

cheap fix

What the code does

The only task lock is in-memory and process-local; the direct engine path doesn't even guarantee exception-safe release. Documentation implies robust pessimistic locking across processes. Deployment is in fact single-process (two uvicorns sharing the DB is a known death-loop incident).

Decision

Document single-process as the supported deployment, or commission a durable lease design?

Recommendation

Document single-process as the constraint (it already is operationally). Durable leases only if multi-process ever becomes a goal. UI consequence: none, beyond not advertising concurrent-operator safety.

Sources: 03 decision 2 + CON-WF-04, 07 §2.

D13 · Small vocabulary rulings

cheap fix

What the code does

Three naming questions the reports escalate: (a) graph-mode failed can be reopened, so "failed" is not absolutely terminal in graph mode; (b) "review readiness" and "merge readiness" are distinct concepts with different evidence scopes; (c) "artifact" currently names four non-equivalent things (expected path, evidence bundle, interaction log, graph file-state record).

Decision

Accept the three rulings for UI vocabulary?

Recommendation

Accept: (a) graph UI shows failed as reopenable; (b) keep the two readiness labels distinct; (c) keep artifact variants separately named — no umbrella "artifact" concept until someone designs one.

Sources: 03 CON-WF-05, 06 §3, 01 §6, 08 §4.

D · Ops backlog (real, not UI-blocking)

Genuine findings that belong in the engineering backlog, not in front of UI design.

D14 · Backup is not crash-consistent on a live DB

backlog

What the code does

create_backup uses shutil.copy2, skips -wal/-shm, no SQLite backup API, no quiescence check; the journal marker is scanned after the copy so concurrent writes drift it; backup_id is UTC-second and can collide; restore_backup performs no replay and skips the server.lock check that rebuild has. The only genuinely bug-shaped finding in the whole exercise.

Recommendation

Backlog ticket. Interim contract: backups valid only against a stopped server (already your practice). Proper fix when picked up: sqlite3.Connection.backup(), collision-safe id, lock check in restore. Was Q-4 — accurate finding, wrong queue.

Sources: 01 §7 + DP-ENT-backup rows, 08 §5.

E · Process

D17 · Freeze the catalog machinery

decide

What happened

The Phase 0–3 pipeline produced ~4 MB of canonical YAML, a 280 KB validator, and a review checkpoint whose questions had lost their meaning through three lossy hops (reports → typed YAML → ID catalogs → generated review). The seven reality audits in agent-reports/01–07 carry ~90% of the value and remain readable and cited.

Decision

Freeze the catalog/ + validate.py layer (no further maintenance, no hash-drift re-audits, phase gates retired) and treat the Markdown reports plus this decision record as the foundation deliverable?

Recommendation

Freeze. Keep the files in-tree as an archive (deleting is a separate cleanup choice). The design phase consumes: the seven audit reports, the JTBD docs, and the answers you record here. Nothing downstream should require the validator to pass.

Outcome (2026-07-26)

Peter amended: delete rather than freeze — "If files shouldn't be referenced we should remove them, otherwise they risk being pulled in again." The catalog layer, generated projections, and their tests were deleted; git history retains them. See DECISIONS.md.
