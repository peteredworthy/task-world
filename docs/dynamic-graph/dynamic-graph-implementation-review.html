Dynamic Graph Implementation Review

task-world · src/orchestrator/graph/ + src/orchestrator/graph_runtime/ + src/orchestrator/workflow/graph_driver.py · ~20,700 lines · reviewed 2026-07-01 · re-assessed 2026-07-03 · status updated 2026-07-05
Verdict. The dynamic graph is an architecturally serious event-sourced execution kernel: a pure command/event/projection core with an effectful shell, transactional outbox, optimistic concurrency, and an unusually disciplined validation culture (FR proof ledger, product-path evidence). Its main risks are internal, not conceptual: a handful of monolithic modules, a growing dual-source-of-truth pattern where command handlers rescan the raw event log instead of the projection, recovery logic accreting into schedule_tick as reactive patches for quiescence bugs, and full-replay costs that grow with every audit event the scheduler emits. All are fixable incrementally without changing the external contract.

1. Architecture overview

The dynamic graph replaces the legacy parent/child oversight carrier with a typed work graph. A routine is compiled (graph/compiler.py) into nodes (worker, verifier, planner, check, gate, join, final_gate, recovery…) and typed edges with port contracts. Planner agents extend the graph at runtime by submitting validated patches, so the graph grows as the run discovers work — this is the "dynamic" part.

2. Strengths

Strength

Pure kernel / effectful shell separation is real, not aspirational

graph/ vs graph_runtime/ · commands.py:89 apply_command · clock.py FakeClock, SequentialIdGenerator

apply_command takes a projection, the event list, a payload, a clock, and an id generator, and returns events — nothing else. Time and identity are injected, so every scheduling, recovery, and validation decision is deterministic and replayable in-memory. This is what makes the 80 graph test files (including per-FR acceptance suites test_graph_fr02…fr17 and test_graph_outbox_crash_points.py) possible and cheap. Rejections are themselves events (command_rejected, patch_rejected), so failed intent is auditable rather than lost in exceptions.

Strength

Correct durability spine: optimistic concurrency + transactional outbox

controller.py:49–99 · store.py:467–520 · outbox.py:79–113

Every command carries an expected_position; a race raises StaleProjectionError, with the DB unique constraint on (aggregate_id, version) as a second line of defense behind the pre-check. Side-effect intent (agent_dispatch_requested, cleanup_requested) is written to outbox rows in the same transaction as the events, and the executor protocol explicitly documents the at-least-once/idempotency contract. Startup recovery (recovery.py + reconcile_runtime) resets in-flight dispatching rows and converts leases whose processes are gone into agent_died. This is the textbook pattern, implemented with the crash points actually tested.

Strength

Patch system treats planner agents as untrusted proposers

patch_validator.py · macros.py · horizon_templates.py · commands.py:_apply_patch_command

Dynamic mutation goes through a validated PatchEnvelope: role-scoped allowed ops (ALLOWED_BY_ROLE — planners cannot create gates), a read-set staleness check that classifies intervening events as invalidating or neutral, planner budgets, and macro expansion. Horizon templates give planners canonical region shapes (discovery → implementation → validation → gap analysis → corrective → final invariant) instead of freeform topology. The design assumption — LLM output is a proposal to validate, not an instruction to execute — is the right one and is applied consistently.

Strength

Resource claim model is unusually thorough

scheduler.py:89–116 claims_conflict · :238–361 path/glob overlap

Claims distinguish read/write/graph_write/review_write/external modes, snapshot-scoped reads (a read pinned to a snapshot doesn't conflict with a write), external resource keys with exclusivity, and path overlap with glob handling and repo-relative normalization that rejects ../ escapes. Deterministic tie-ordering (priority, kind, region order, creation position, node id) makes scheduling reproducible, and every deferral records a machine-readable reason (node_deferred with resource_conflict:write:write etc.), which feeds directly into the observability story.

Strength

Observability as projections, plus read models for cost

projections.py: 35+ project_* functions · store.py: event summaries, node-detail read models, projection snapshots, field-extracted light reads

/graph/final-blockers, scheduler view, lease view, decision view, planner freshness packet, residue report — the run's state is explainable from durable events, and the dogfood pause diagnosis in status.md shows these readbacks doing real diagnostic work. The store layer adds pragmatic performance escapes: JSON field extraction to avoid hydrating full payloads (read_run_light), persisted event summaries, and node-detail read models maintained incrementally on append.

Strength

Operational defense in depth

graph_driver.py:388–434, 509–521 · dispatch.py:_bounded_prompt · gatekeeper.py

The driver snapshots the main worktree's dirty set before driving and flags any leaked paths after (a direct response to the June worktree-escape incidents); prompts are size-bounded (the E2BIG fix); a signature-based no-progress guard converts silent stalls into a recoverable graph_blocked pause instead of a spinning loop; leases expire and renew; the gatekeeper classifies worktree residue against a taxonomy. Each guard traces to a real incident — the system is absorbing its operational history.

Strength

Validation culture: proof ledger over test-passing

docs/dynamic-graph/status.md · typed-work-graph-requirements.md · complete/true-comparison-results.md

FR-01…FR-18 were closed only with product-path evidence (real runs through the API/runtime surface with observable readbacks), tests explicitly demoted to regression evidence. The true-comparison study measured real cost (dynamic ≈ $0.77/run, ~3-agent-equivalent cost with structural correctness guarantees). This discipline is rare and is the reason the June dogfood found the task-region fulfillment bug at all.

W3 — Full replay per command, and the scheduler inflates the log it must replay

controller.py:62–71 read_run + rebuild_projection every command · store.py invalidate_projection_snapshot on append · commands.py:2324–2431 node_deferred per tick

Partially improved: the fold-once series (8892968a5…c11b04f95) removed redundant re-folds on the read path — API views and the evidence digest now fold once (digest ~10s → ~1.8s). Unchanged: every handle_command still reads the full event stream and folds from scratch — O(n) per command, O(n²) over a run's life. The store has a projection snapshot read model, but the controller's write path never uses it, and appends invalidate the snapshot rather than folding new events into it. schedule_tick still persists node_deferred audit events on every tick for every ineligible node, so the polling drive loop grows the log even when nothing happens — inflating replay cost and forcing the driver's signature-based progress check because raw position always advances. Startup recovery still replays every run in the database. Spec: w3-incremental-snapshots-spec.md.

2026-07-05: Implemented and verified by run 88f46a2e (snapshot+tail write path with PROJECTION_SCHEMA_VERSION, deferral dedup, terminal-run skip in startup recovery; +283 lines store.py, +547 projections.py) — but not merged: uncommitted in worktrees/r356, base f526cd70a, conflicts with main's rewritten handle_command (read-outside-lock, uncommitted). The cost of not landing it was demonstrated live on 2026-07-05: full-log JSON parses per command at 3.15 GB DB pinned the worker at 100% CPU, starved lease renewals, expired a live verifier's lease, and made the REST API unresponsive — the run's own bookkeeping starved the run. Interim mitigations on main: fold-once reads (merged), BEGIN IMMEDIATE (merged), read-outside-lock + payload trim 28.8→1.77 GB (uncommitted). New-event bloat continues until W5 lands.

Medium

W6 — Outbox dispatcher is serial, backoff-free, and dead-ends quietly (unchanged)

outbox.py:125 max_attempts=3 · :149 immediate re-pending · :227–233 _mark_failed_attempt → OUTBOX_FAILED dead-end · spec: w6-outbox-hardening-spec.md

Dispatch claims one row per DB transaction and executes side effects strictly sequentially — independent agent dispatches for parallel-safe nodes still serialize through the dispatcher (the executor tracks concurrent processes, but rows are dispatched one at a time). A failed attempt goes straight back to pending with no backoff, so a deterministic failure burns all 3 attempts in quick succession, after which the row sits in failed with no readback, alert, or requeue path surfaced in the graph API. Recovery redispatches pending/dispatching but not failed.

2026-07-05: Still open as specced. Adjacent-but-different fix landed: d390f6c41 added _retry_locked (exponential backoff on lock-class OperationalError) around outbox bookkeeping — the success-path crash from project_driver_db_locked_crash.md — plus WAL + busy_timeout. Attempt-level backoff, failed-row surfacing, and requeue remain untouched.

Medium

W7 — Heuristic glob-overlap check can under-detect conflicts (unchanged)

scheduler.py:333–344 _literal_prefix_may_match_glob probes ("x", "x.py", "nested/x.py") · :339 _glob_prefixes_may_overlap static-prefix comparison · spec: w7-glob-overlap-spec.md

Whether a literal claim path sits "under" a glob claim is decided by probing three synthetic suffixes; a pattern whose match depth exceeds the probes (e.g. src/*/*/gen/*.py vs literal src/a) can be judged non-overlapping, letting two writers into overlapping paths — the exact safety property claims exist to enforce. Glob-vs-glob comparison falls back to static prefixes, which is conservative but returns True for any two rootless patterns, over-serializing. Empty path lists also conflict with everything, which is safe but silently defeats parallelism when a claim is sloppily specified.

2026-07-05: Unchanged — probes and static-prefix fallback still in place (scheduler.py:330–344). No spec run scheduled yet.
