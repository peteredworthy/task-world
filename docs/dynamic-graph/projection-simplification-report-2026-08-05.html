Architecture review · read-only analysis

The projection is over-protected, not merely over-grouped.

The twelve lifecycle groups are defensible. Most of the new complexity comes from enforcing deep immutability at every reachable value, duplicating already-typed records, validating a disposable checkpoint like an authoritative database, and maintaining broad compatibility/readback surfaces around the projection.

Current checkout reviewed 5 August 2026 · No production code or behavior changed

Recommended direction

Keep events immutable and keep one grouped projection as the read source. Make the projection an owned, private accumulator; reuse canonical record models; store a dedicated checkpoint with schema, position, and checksum; and expose only the read queries the application actually uses.

This preserves replay, snapshot+tail performance, optimistic concurrency, and final-invariant behavior while removing much of the machinery whose only job is defending the projection from its own code.

Treat the checkpoint as a disposable cache, not a second authority

The checkpoint codec is 1,811 lines, backed by a 1,405-line relationship-policy artifact and roughly 2,540 lines of codec/integrity tests. It performs canonical JSON scanning, model reconstruction, identifier-path discovery, policy compilation, and cross-group referential validation. That is disproportionate for state that is explicitly disposable and rebuildable from authoritative events.

Replace with: schema version + event position + serialized grouped state + checksum; validate with Pydantic on load; if decoding, checksum, or a small set of critical invariants fails, discard and rebuild. Enforce relationship correctness when events are accepted and when reducer code writes indexes, where the fault originates.

StrategicHigher migration risk

Move immutability to the ownership boundary

The current reducer pays for persistent data structures on every event: custom FrozenMap, recursive JSON freeze/thaw, strict frozen models, 57 model_copy calls and 65 map_set calls in projections.py. The controller, however, loads a projection for a command, uses it locally, and commits new events; it does not require arbitrary consumers to retain and mutate the same object graph.

Replace with: an owned mutable builder used only while folding a command/replay, then a validated snapshot at the checkpoint/query boundary. Keep the reducer deterministic and side-effect-free from the caller’s perspective by never sharing the builder. Immutable event envelopes remain unchanged.

projection_collections.py (249 lines); projections.py:492–578 and reducer update sites; test_graph_projection_immutability.py plus collection/model tests.

Separate the runtime checkpoint from the bounded API snapshot

GraphProjectionSnapshotModel stores compact public fields and embeds the full runtime checkpoint inside its decisions JSON. The same write path then byte-bounds the owner and may drop that checkpoint when it exceeds 262 KiB. Public reads accept the packed form, while runtime reads require a full integrity-decodable form. One row is serving two incompatible lifecycles.

Change: store the internal checkpoint in a dedicated table/column without response-size packing. Keep the compact /graph read model separate. This removes conditional “packed but healthy for API / invalid for runtime” logic and prevents graph size from disabling snapshot+tail command handling.

db/orm/models.py:378–396; graph_runtime/store.py:6135–6250; read_current_projection_snapshot versus read_projection_checkpoint.

Retire the coupled archival-view feature unless external clients truly need it

Opening the graph panel launches an extra anchor request plus three archival requests for topology, final blockers, and regions. The product UI renders only their position, total_known counts, and a partial-data note—it does not render the returned topology, blocker rows, or regions. Supporting those counts currently requires three entry tables, a checkpoint table, a background maintenance worker, coupled publication/rollback logic, pagination/byte-packing, three endpoints, and extensive integration tests.

Remove or narrow: delete topology/region archival materialization and show counts already available from the compact health/projection view. Preserve final-invariant computation and failed-outbox blocking in completion/health. If the detailed endpoints are a public contract, deprecate them first or move them behind an explicit diagnostics export.

Delete bespoke boundary enforcement after the boundary becomes small

An 864-line AST checker and a 2,227-line test file enforce that exactly five files may touch grouped storage. That enforcement was a rational response to a very broad public projection API; it should not become permanent architecture. Once the projection is private and consumers use a small query module, ordinary module visibility, top-level import checks, and focused architectural tests are enough.

Remove: five-file allowlist machinery, provenance code, and exhaustive checker self-tests. Retain one short rule that production modules outside graph import through the public package.

Decision scenarios

Savings are relative to the 24,210-line direct surface and include tests/config/tooling. They are directional, not a commitment estimate.

  • Prune queries/exports.
  • Remove unused projectors.
  • Shrink boundary tests.
  • Keep deep immutability and codec.

5–8k lines

About 21–33% of the direct surface.

  • All conservative work.
  • Dedicated runtime checkpoint.
  • Canonical record reuse.
  • Simpler cache validation.
  • Owned builder or staged move toward it.

Aggressive product trim

8–12k lines

About 33–50% of the direct surface plus adjacent API/runtime code.

  • All balanced work.

  • Narrow diagnostic endpoints.
  • Remove coupled UI fetches.

What should and should not disappear

Keep these invariants

  • Events remain the durable authority.
  • Commands read one folded projection, never ad-hoc raw-event scans.
  • Snapshot+tail remains the runtime path.
  • Position checks preserve optimistic concurrency.
  • Canonical event and record payloads remain Pydantic-validated.
  • Final-invariant and failed-outbox blocking remain authoritative.
  • Replay parity and a realistic performance gate remain.

Remove these implementation obligations

  • Deep immutability for every internal nested value.
  • Persistent-map identity preservation across reducer updates.
  • A second projected record type hierarchy.
  • Relationship-policy discovery for a disposable cache.
  • A broad public query API with no application consumer.
  • One storage row serving runtime checkpoint and bounded API response lifecycles.
  • Materialized diagnostics whose data the product does not display.

Method and confidence

Evidence reviewed

Projection models, collections, queries, codec, reducer, public exports, boundary checker, relation-policy artifact, runtime checkpoint/store paths, graph API routes, ORM read models, GraphPanel hooks/rendering, architecture documentation, and the direct projection test closure.

Static metrics used Python AST parsing and text counts. Query reachability started from production imports (excluding the package re-export file) and followed direct same-module function calls.

Limits

This is a current-checkout review, not a history/diff attribution exercise. It did not use production telemetry or inventory clients outside this repository. The archival endpoint recommendation is therefore conditional on confirming there are no relied-upon external consumers.

Line-reduction ranges overlap—especially codec, duplicate records, immutability, and boundary tests. They should be re-estimated after each stage rather than summed.
