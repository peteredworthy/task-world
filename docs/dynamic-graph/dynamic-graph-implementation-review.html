Verdict. The dynamic graph is an architecturally serious event-sourced execution kernel: a pure command/event/projection core with an effectful shell, transactional outbox, optimistic concurrency, and an unusually disciplined validation culture (FR proof ledger, product-path evidence). W1-W4 addressed the original highest-risk implementation defects: projection-first reads are now enforced for the former raw-scan helpers, recovery moved toward source transitions plus an explicit reconcile command, command execution uses incremental projection checkpoints, and the worst dispatch/prompt and command-dispatch monoliths have been split. Since the 2026-07-06 reassessment, W6 outbox hardening, W7 segment-wise glob overlap, and W8 drive-loop/export cleanup have landed. The remaining risks are narrower: the core still handles many graph facts as untyped dictionaries and outbox dispatch is still serial. The driver remains a poll loop, but its incident guards now have explicit source-bound retirement conditions; event-triggered driving is not a prerequisite for retiring them.

1. Architecture overview

The dynamic graph replaces the legacy parent/child oversight carrier with a typed work graph. A routine is compiled (graph/compiler.py) into nodes (worker, verifier, planner, check, gate, join, final_gate, recovery…) and typed edges with port contracts. Planner agents extend the graph at runtime by submitting validated patches, so the graph grows as the run discovers work — this is the "dynamic" part.

── write path ────────────────────────────────────────────────────────── routine ─▶ compile_routine ─▶ seed events API / driver ─▶ GraphController.handle_command(run_id, expected_position, cmd) ├─ load_projection_with_tail # snapshot + event tail outside write lock ├─ apply_command # pure registry facade over graph/_commands.py ├─ BEGIN IMMEDIATE + current_position re-check ├─ append_events + advance projection checkpoint └─ append_outbox_rows # same transaction — transactional outbox OutboxDispatcher ─▶ GraphDispatchExecutor ─▶ agent runner / check / gate / join agent callbacks ─▶ submit_callback / submit_patch commands ─▶ new events ── read path ─────────────────────────────────────────────────────────── checkpoint/tail or summaries ─▶ projections.py (35+ project_* readbacks) ─▶ API /graph/* views ── loop ──────────────────────────────────────────────────────────────── GraphRunDriver.drive_to_quiescence: schedule_tick ─▶ dispatch ─▶ wait ─▶ repeat

2. Strengths

Strength

Pure kernel / effectful shell separation is real, not aspirational

graph/ vs graph_runtime/ · commands/__init__.py apply_command registry · clock.py FakeClock, SequentialIdGenerator

apply_command takes a projection, the event list, a payload, a clock, and an id generator, and returns events — nothing else. Time and identity are injected, so every scheduling, recovery, and validation decision is deterministic and replayable in-memory. This is what makes the 80 graph test files (including per-FR acceptance suites test_graph_fr02…fr17 and test_graph_outbox_crash_points.py) possible and cheap. Rejections are themselves events (command_rejected, patch_rejected), so failed intent is auditable rather than lost in exceptions.

Strength

Correct durability spine: optimistic concurrency + transactional outbox

controller.py:45–121 · store.py:824–849, 981–1014 · outbox.py:79–124

Every command carries an expected_position; a race raises StaleProjectionError, with the DB unique constraint on (aggregate_id, version) as a second line of defense behind the pre-check. W3 improved the write path: the expensive projection fold now loads a persisted checkpoint and only folds the event tail before the write lock, then the transaction re-checks the head and advances the checkpoint with the append. Side-effect intent (agent_dispatch_requested, cleanup_requested) is written to outbox rows in the same transaction as the events, and the executor protocol explicitly documents the at-least-once/idempotency contract. Startup recovery (recovery.py + reconcile_runtime) resets in-flight dispatching rows and converts leases whose processes are gone into agent_died. This remains the right durability pattern, now with the replay-cost fix landed.

Strength

Patch system treats planner agents as untrusted proposers

patch_validator.py · macros.py · horizon_templates.py · _commands.py:_apply_patch_command

Dynamic mutation goes through a validated PatchEnvelope: role-scoped allowed ops (ALLOWED_BY_ROLE — planners cannot create gates), a read-set staleness check that classifies intervening events as invalidating or neutral, planner budgets, and macro expansion. Horizon templates give planners canonical region shapes (discovery → implementation → validation → gap analysis → corrective → final invariant) instead of freeform topology. The design assumption — LLM output is a proposal to validate, not an instruction to execute — is the right one and is applied consistently.

Strength

Resource claim model is unusually thorough

scheduler.py:89–116 claims_conflict · :238–361 path/glob overlap

Claims distinguish read/write/graph_write/review_write/external modes, snapshot-scoped reads (a read pinned to a snapshot doesn't conflict with a write), external resource keys with exclusivity, and path overlap with glob handling and repo-relative normalization that rejects ../ escapes. Deterministic tie-ordering (priority, kind, region order, creation position, node id) makes scheduling reproducible, and every deferral records a machine-readable reason (node_deferred with resource_conflict:write:write etc.), which feeds directly into the observability story.

Strength

Observability as projections, plus read models for cost

projections.py: 35+ project_* functions · store.py: event summaries, node-detail read models, projection snapshots, field-extracted light reads

/graph/final-blockers, scheduler view, lease view, decision view, planner freshness packet, residue report — the run's state is explainable from durable events, and the dogfood pause diagnosis in status.md shows these readbacks doing real diagnostic work. The store layer adds pragmatic performance escapes: JSON field extraction to avoid hydrating full payloads (read_run_light), persisted event summaries, and node-detail read models maintained incrementally on append.

Strength

Operational defense in depth

graph_driver.py:388–434, 509–521 · dispatch.py:_bounded_prompt · gatekeeper.py

The driver snapshots the main worktree's dirty set before driving and flags any leaked paths after (a direct response to the June worktree-escape incidents); prompts are size-bounded (the E2BIG fix); a position-based no-progress guard converts silent stalls into a recoverable graph_blocked pause instead of a spinning loop; leases expire and renew; the gatekeeper classifies worktree residue against a taxonomy. Each guard traces to a real incident — the system is absorbing its operational history.

Strength

Validation culture: proof ledger over test-passing

docs/dynamic-graph/status.md · typed-work-graph-requirements.md · complete/true-comparison-results.md

FR-01…FR-18 were closed only with product-path evidence (real runs through the API/runtime surface with observable readbacks), tests explicitly demoted to regression evidence. The true-comparison study measured real cost (dynamic ≈ $0.77/run, ~3-agent-equivalent cost with structural correctness guarantees). This discipline is rare and is the reason the June dogfood found the task-region fulfillment bug at all.

W3 — Full replay per command, and the scheduler inflates the log it must replay

merged as 0a5e1b0ba · controller.py load_projection_with_tail before BEGIN IMMEDIATE · store.py advance_projection_snapshot

Current state: closed for the original W3 scope. GraphController.handle_command now loads the latest valid projection checkpoint plus tail outside the write lock, validates the expected position, applies the pure command, then performs a short BEGIN IMMEDIATE transaction that re-checks the head, appends events/outbox rows, and advances the checkpoint. Startup recovery also skips terminal checkpointed runs. The old recommendation to add incremental snapshots is no longer relevant; the remaining performance/driver work is W8 follow-up around package exports, explicit stopgap retirement, and possible event-triggered driving.

5. Entropy: where recent changes broke the system, and how to evolve without breaking

The P1 closure is a useful natural experiment: seven kernel-level fixes landed in three days, and the commit history records exactly where the system resisted change and where it tore. Three failure modes account for all of the breakage; the 2026-07-07 PM module sweep confirmed the first is still active, re-scoped the third, and added a fourth that produces cruft rather than incidents.

Entropy 1

Derived read models drift because field propagation is manual

store.py:234 GRAPH_PROJECTION_PAYLOAD_FIELDS + 3 sibling allowlists · broke in 4f2cb0f58 (2nd occurrence; 1st was attempt_number)

What happened. P1 #3 and #7 added new payload fields the reducers read (decision, gate_id, approved, appeal_type, supersedes_task_region_id(s)). The compact read path reconstructs events via SQL json_extract over a hand-maintained field tuple, so the new fields were silently absent from compact projections and snapshots — full replay and checkpoint reads disagreed until 4f2cb0f58 patched the tuple and added a state-matrix parity test.

Why the design tears here. The information "reducer X reads payload key K" exists in one place (_commands.py/projections.py) and must be manually mirrored into a second place (store.py) with no compiler, test, or runtime check connecting them. Every performance-motivated derived read model (light reads, summaries, node detail, compact projection) multiplies the mirror count. This is the same multi-source-of-truth family as pre-W1 raw scans — W1 unified who folds; the field allowlists re-introduced what gets folded as a second truth.

Engineering for evolution. Make the schema the artifact that changes, not the mirrors: typed payload models (W5) that both the reducers and the extraction lists are generated from; or an automated corpus-replay parity test (fold full events vs compact events for every recorded fixture run, diff projections) so any missed field fails CI the day it is introduced rather than in the next incident. The manual matrix tests added in 4f2cb0f58 protect only the states someone thought to enumerate.

Third occurrence, found 2026-07-07 PM: the sweep confirmed the family is still producing bugs — store.py:_scheduler_view_from_projection, a hand-written duplicate of project_scheduler_view on the incremental-snapshot path, has drifted (missing max_grants_reached exclusion; §4 P0 #1). The full mirror census is seven instances, one guarded (§4 P1 #5). The prediction in this card held exactly: the unguarded mirrors diverged first.

Entropy 2

Work developed off stale bases arrives as archaeology, not merges

W2–W4 backlog (base f526cd70a) · P1 chain: 8a20597c8 → fd219ae60 → 5b76e5cfe "Port … to main" → 4f2cb0f58 → 7d60173c0

What happened. The P1 fixes were developed and then had to be ported to main, followed by two repair rounds ("Fixes for P1 fixes", "Fixes for Fixes for P1 fixes") and two ledger-gap closures where the docs claimed Fixed ahead of the tree: the final-invariant template still wired the brittle verifier-corrective-{region_id} node id, and the claude_sdk gate-off wasn't actually in SUPPORTED_GRAPH_RUNNER_TYPES until 7d60173c0. Same shape as the July W-spec merge backlog.

Why the design tears here. Graph runs execute in isolated worktrees (correctly, per the incident history), but nothing records or checks the seed SHA against the integration branch, and nothing forces "run verified" to mean "merged and verified on main". The gap between those two states is where every fixes-for-fixes chain has originated.

Engineering for evolution. P0 #2: seed-SHA recording + staleness refusal at run creation, and a merge-back convention where the port commit cites source run + base SHA. The p1-resolution-ledger.md closure rule (no "Fixed" without a named test re-run green) is the right complement and demonstrably worked — it caught both doc-ahead-of-code gaps — so extend the ledger pattern to future W-spec closures.

Entropy 3

Policy accretes in the effectful edges faster than the kernel absorbs it

graph_driver.py 1,250 lines · dispatch-side codex submit-rejection detection · poison-pattern lint · outbox retry waiting

What happened (pattern, not a single break). Each incident deposited a guard at the layer where it was observed — driver progress signatures, dispatch output sniffing, recovery no-ops, template lints — and the later, correct kernel fix (reconcile, dead-input events, wildcard evidence edges, late-callback acceptance) did not automatically retire the stopgap. W8 removed two concrete examples (the recovery no-op and progress signatures), but the driver still carries incident-era control flow whose triggering conditions should be periodically checked against newer kernel behavior.

Why the design tears here. The kernel is cheap to change safely (pure, replayable, 80+ test files); the edges are expensive (async, DB, processes). Under incident pressure, fixes land where reproduction is fastest — the edges — so entropy concentrates exactly where tests are weakest. Stopgaps without retirement conditions become permanent load-bearing behavior.

Engineering for evolution. Treat every edge-layer guard as a numbered stopgap with an explicit retirement condition ("delete when kernel emits dead-input events" — that condition is now true). W8 remains the concrete vehicle: after each kernel capability lands, sweep the driver/dispatch/recovery layer for guards it obsoletes. The heuristic worth institutionalizing: if a fix can be expressed as a command/event/projection rule, it belongs in the kernel even when the incident was observed at an edge — the P1 batch shows the kernel versions were all achievable and all landed with deterministic tests.

Closeout 2026-07-18: every remaining edge guard is mapped in guard-retirement-ledger.md; contamination, lease recovery, reopen, crash, stale/SQLite retries, outbox timing, callback rejection, compromised state, startup recovery, redispatch, and terminal filtering remain load-bearing. The misplaced pure projection-derived classification moved into the kernel in f0b6c237d, with duplicate driver policy removed in 2ccd20bce. Event-triggered driving is neither evidence for deletion nor a prerequisite.

Entropy 4

Features are retired by gating, not by deletion — carcasses accumulate behind the gate

claude_cli graph-patch bridge (~120 unreachable lines) · dead original apply_command dispatcher (_commands.py:103) · codex callback_channel knob · 5 unconsumed diagnostic endpoints · 3 byte-identical duplicated test files

What happened (pattern). When behavior is retired here, the mechanism is a boundary gate: SUPPORTED_GRAPH_RUNNER_TYPES narrows, a facade registry supersedes a dispatcher, a REST path is replaced by an MCP tool. The gate is tested (well — the retirement guards are among the best tests in the suite), but the code behind the gate stays: the claude_cli sentinel bridge can never execute yet still shapes prompts-code reading; the pre-W4 apply_command if-chain sat dead next to its replacement; callback_channel still renders as an operator-facing choice while a parity test proves both values identical; diagnostic endpoints built for acceptance evidence never gained a consumer. Test files were copied between tests/unit/ and tests/integration/ during the W-series reorganization instead of moved.

Why the design tears here. Gating is cheap and safe under incident pressure (one line, one test); deletion requires proving unreachability across module boundaries, which nobody owns as a step. The event-sourced discipline makes the system tolerant of dead code — nothing breaks — so there is no forcing function. The cost is paid by readers: dead paths are indistinguishable from live ones without the reachability argument, and the next contributor extends the carcass (or the UI keeps offering a knob that does nothing).

Engineering for evolution. Make deletion part of the retirement definition-of-done: a retirement isn't closed until the unreachable code is removed in the same or a named follow-up commit, with the retirement guard test as the safety net. The §4 P2 table is the backlog this rule would have prevented; clearing it is one focused PR precisely because every item is already verified unreachable.
