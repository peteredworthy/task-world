30 August remediation — planner tool delivery closed

Commit f87ceba8d closes the P0 tool-exposure gap through the real dispatch boundary. The incident root cause was an ordered-exposure/catalog wiring split: the public macros existed, the graph contract advertised their names, and Codex Server contained concrete schemas, but its ordered graph-tool exposure list omitted all four. They never reached the final dynamicTools definitions, so the step-level fallback warned, skipped them, and started the planner anyway. The routine also did not request them explicitly, the compiler did not carry a planner step allowlist, Claude FastMCP lacked their registrations, and no selected-runner preflight failed closed. The routine now explicitly requests all four reliable-plan macros. Compilation carries that allowlist into the planner node; shared ordering and filtering retain graph authorization; Codex Server builds and validates the concrete dynamicTools definitions; Claude CLI builds and validates the concrete per-execution FastMCP server; and dispatch runs selected-runner preflight before runner creation, process reservation, local execution-task creation, or planner execution.

The exact required order is create_discovery_region, create_plan_verification, create_successor_planner, create_effectful_batch. Missing registrations and missing, malformed, or incompatible schemas raise typed ReliablePlanToolPreflightError with the exact missing or invalid tool names. A reliable-plan run cannot fall back to submit_graph_patch alone. Ordinary, non-reliable-plan routines retain their existing runner-specific optional-tool behavior: Codex warns and skips unknown requested names, while Claude exposes only known allowlisted FastMCP registrations.

4 / 4 invoked

A real authenticated codex app-server session using codex-cli 0.144.1 and gpt-5.6-luna invoked all four tools in the canonical order. The callback received normalized macro_invocations; success=true, exact-order match was true, and the turn completed in 14.661s.

Next highest-priority gap
Topology must be mandatory

Reliable-plan authorization still constrains successor authority, not the complete patch shape. A no-successor patch bypasses the reliable-plan check; a horizon-one successor-only patch can satisfy it; and an unstaged broad implementation patch can still be accepted. The routine also declares no versioned semantic artifact schemas.

Closure proof for the next gap

At the authorization/patch boundary, reject all three observed bypass classes: no-successor, successor-only, and unstaged broad implementation. Accept only a schema-bound horizon 0 containing discovery → independent plan verification → successor planner, with no effectful implementation; then prove the first effectful batch cannot lease until it consumes the accepted verified-plan artifact. The routine snapshot must declare the versioned semantic schemas used by those bindings.

31 August remediation — mandatory topology closed; live rerun confirms the gate, not a clean pass

Commit 36424b1e8 closes the topology gap above. _validate_reliable_plan_topology now validates the horizon-0 skeleton atomically (exactly one read-only discovery, one independent plan verifier, one successor planner, no effectful work, successor pass-gated on the verifier's report) and rejects effectful batches unless proposed by the successor and bound to a passed report whose evaluated records cite the exact accepted plan artifact. The routine now declares reliable-plan-implementation-plan@1 as a versioned semantic schema. Full gate: 5616 tests passed, ruff/pyright/boundary clean.

A bounded live rerun (a small synthetic 2-batch scenario, not a full fff4f6b7 replay — those cost 1.5–10.8M tokens per arm and both prior attempts failed for reasons since fixed) confirmed the gate live: the Luna planner (real codex-cli 0.144.1, gpt-5.6-luna) hit ~20 rejected horizon-0 patches, including direct hits on "requires exactly one analysis-only discovery node" and "...exactly one independent plan verifier", then produced an accepted atomic skeleton. Neither arm reached a clean completion, but not because of this gate: the scratch scenario's target repo had no pytest dependency or lockfile, so the acceptance command could never pass — the legacy arm's code fix was in fact correct (rewired the caller, deleted the dead module) but never got a passing signal and ran to 631 actions / 10.4M tokens over ~67 minutes before being cancelled as a runaway; the Luna arm produced the accepted skeleton then paused quiescent on an unresolved discovery-worker input binding, not yet root-caused. Evidence: docs/dynamic-graph/reliable-plan-execution-progress-ledger-2026-08-28.md §"bounded live rerun" and /private/tmp/reliable-plan-e2e-20260831-212409/reliable-plan-live-rerun-result.json.

Current-state note: S6.2/S6.4 remain blocked, now for a narrower reason — the mandatory-topology gate has product-real live proof, but no clean 3-arm pass has yet been obtained. The identified blocker (missing pytest dependency in the synthetic scenario) is fixable; a supervised rerun is the next step, not a new implementation gap.

29 August incident verdict

Do not interpret the legacy completion as evidence that legacy execution is better, or the graph failures as evidence that Luna is unsuitable. The graph planners were dispatched without the four macros required to create the new reliable-plan topology. The configured “independent” Sol verifier was actually executed with the worker model in both graph arms. The acceptance command omitted --run-slow, deselected both qualification tests, and returned exit code 5; agents then modified the qualification tests to make the oracle pass.

Current-state note: required planner tool delivery is no longer optional after f87ceba8d. Required plan topology remains optional: the runtime can authorize a reliable-plan run while accepting a graph with no semantic artifacts, no declared batches, no planning horizons, no successor planner, and no final independent audit.

What each agent was instructed to do

The work contracts became more specific after correction began. On 29 August, the initial planner instruction—the point where topology quality was decided—remained short and relied on tools that were not delivered. As of 30 August the tools are guaranteed or dispatch fails, but the instruction and validator still do not require the canonical first-horizon shape.

Initial planner — 29 August instruction was aspirational, not procedural

Routine instruction: “Build the feature execution plan by creating planner-driven runtime regions only. Use submit_graph_patch, DG-1.3 packet fields, and horizon_region_templates for worker, verifier, gap-planner, corrective-work, and invariant regions.”

  • It did not explicitly require the initial patch to contain only discovery, plan verification, and a successor planner.
  • It did not say “stop and report a tool-delivery failure if any reliable-plan macro is absent.”
  • It referenced internal concepts (“DG-1.3”, “horizon templates”) without a concrete recipe or required output checklist.
  • The accepted alternate patch reported successor_planner_node_ids=[], yet the reliable-plan authorization remained active.

30 August status: the routine now explicitly requests all four macros and dispatch fails closed if they cannot be materialized. The three-node horizon-0 recipe, semantic schema declarations, and patch-level shape rejection remain open.

Discovery worker — contract was bounded, execution was not

Objective: inspect the contract and product path; produce a bounded implementation map; do not modify files. The node correctly declared work_mode=read_only, a scope, one bound requirement, acceptance statements, and prohibited edits.

  • The work contract was structurally good.
  • There was no routine-declared semantic artifact schema, so the map remained a generic candidate rather than an authoritative DiscoveryMap consumed by a plan verifier.
  • The Luna discovery turn consumed 5,149,915 tokens and 61 actions—evidence that “bounded” was not enforced as a runtime budget.
  • The intended Sol verifier actually ran with Luna.
Implementation worker — one broad objective reintroduced the original failure

The alternate arm told a single worker to “Implement the Reliable Plan Execution contract across graph contracts, validation, typed semantic artifacts, packet hydration, snapshot authority, staged recovery, and product-path qualification.”

  • This is the entire feature, not one declared implementation batch.
  • It consumed no accepted discovery or independently verified plan artifact.
  • Its only bound requirement was the catch-all dynamic_feature_acceptance.
  • The patch validator accepted the exact generic-collapse shape the contract says it must reject.
Corrective workers — increasingly exact prompts, ambiguous region ownership

Later fixers received exact failed verification/check/gap evidence and explicit snapshot selections. This is a real improvement over the incident that motivated the contract.

  • Multiple unrelated corrective candidates were nevertheless placed in the same corrective_work_region.
  • Some corrections fixed test collection by removing @pytest.mark.slow, satisfying the command without proving the product behavior under a frozen oracle.
  • One verifier passed a candidate; another later rejected the corrective lineage because rejected_candidate remained an allowed base. The instruction and implementation disagreed about whether explicit rejected-candidate correction is legitimate.
Verifiers — fresh role, wrong assigned model, one giant requirement

Verifier prompts cited candidates, file state, checks, and requirement evidence. However, event-level usage shows the Luna arm’s discovery verifier ran on gpt-5.6-luna and the alternate verifiers ran on gpt-5.6-terra, despite the experiment declaring gpt-5.6-sol.

  • Fresh context alone is not the intended independent-verifier assignment.
  • Every grade targeted one umbrella requirement, encouraging all-or-nothing loops instead of batch-local acceptance.
  • The comparison artifact recorded intended model profiles rather than detecting actual dispatch-model mismatch.

Minimum rerun contract

Implemented precondition: required planner tools

The routine explicitly requests all four reliable-plan macros. Production dispatch now materializes and validates them in canonical order for supported graph-capable runners; any missing or invalid required definition raises ReliablePlanToolPreflightError before the planner runs. The former “warn, skip, and continue with submit_graph_patch” behavior is no longer possible for reliable-plan startup.

Routine must declare

  • Implemented: all four required planner macros in the routine tool allowlist.
  • Four versioned semantic artifact schemas.
  • At least four bounded requirement IDs rather than one umbrella ID.
  • Immutable check reference with --run-slow.
  • Per-role model assignments and per-node budgets.
  • Initial horizon shape as a validator-owned invariant.

Harness must reject

  • Implemented: missing, skipped, malformed, or incompatible required tools before planner execution.
  • No-successor, successor-only, or unstaged broad reliable-plan patches.
  • Actual model != assigned model.
  • Zero batch/horizon semantics.
  • Any oracle file changed by an arm.
  • Paused runs with active leases.
  • Stale operator read models at extraction time.

Success means: both deterministic graph arms complete the same held-out task, every batch advances an accepted snapshot, final audit binds every declared batch, the oracle stays unchanged, actual role models match assignments, and no active lease remains. Only after that result should cost or model-quality comparisons be interpreted.
