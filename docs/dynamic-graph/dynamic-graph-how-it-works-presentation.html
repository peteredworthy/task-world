How the Dynamic Graph Gets Work Done

A product-facing tour of graph-mode execution: which nodes exist, what agents are prompted with, how scheduling chooses work, how planners add new nodes, and how evidence moves from raw agent output to durable completion.

event sourced typed contracts lease scheduled planner mutable evidence driven

Primary code paths: src/orchestrator/graph/, src/orchestrator/graph_runtime/, src/orchestrator/workflow/graph_driver.py

Mental model

The graph is a durable work ledger, not a prompt conversation

Events

Every fact is appended as a graph event: nodes, edges, accepted records, leases, patch decisions, lifecycle transitions, and failures.

→

Projection

Pure reducers derive run state, node state, input bindings, task acceptance, scheduler queues, leases, final blockers, and read models.

→

Runtime

The controller applies commands, the outbox dispatches side effects, agents submit callbacks, and new events advance the graph.

The controller is the only accepted graph mutation path. Agents can propose work, but accepted events are produced by the kernel after validation.

Sources: graph_runtime/controller.py, graph/projections.py, graph/commands.py, graph_runtime/outbox.py

Lifecycle

A graph run starts as compiled routine facts

1Run startsGraph driver sees execution_mode=graph and ensures the run row is active.
2Seed graphThe embedded routine compiles to root, routine-snapshot, requirements, initial planner/task nodes, checks, and edges.
3Bootstrap lifecycleThe graph accepts and starts itself through accept_run and start commands.
4Drive loopRepeated schedule_tick, outbox dispatch, wait for agents/checks, project state, and continue.
5QuiesceIf no ready, active, or schedulable nodes remain, complete only if final invariants allow it; otherwise pause as graph_blocked.

Contracts

Ports make evidence routable and prompts bounded

Node contracts define

  • handler type: controller, agent, human, or deterministic command;
  • allowed roles and graph tools;
  • input and output ports;
  • record types and schemas per port;
  • fulfillment contribution: task acceptance, control progress, final invariant, or none.

Edges define

  • from_port and to_port compatibility;
  • whether the edge is required;
  • binding policy such as bind_first, bind_latest, or bind_all;
  • record selectors, for example only accepted candidate or failed check_result records;
  • prompt hydration policy: inline summary, structured JSON, artifact reference, or tool-only.

Sources: graph/contracts.py, graph/commands.py

Checks and completion

Passing prompts is not enough; final invariants decide completion

Check nodes

  • must have command_definition or command_binding;
  • run in the correct worktree or snapshot context;
  • record command identity, stdout, stderr, exit code, duration, and evaluated evidence;
  • can use hidden command bindings such as dynamic_feature_hidden_oracle without exposing secrets in planner prompts.

Final blockers

  • run not active or terminal mismatch;
  • active leases or schedulable work remains;
  • task regions not accepted;
  • failed check results;
  • missing passed completion decision;
  • failed nodes, open gates, stale/suspect evidence, or unresolved recovery paths.

Sources: graph_runtime/dispatch.py, graph/projections.py, graph/commands.py

Recovery

Failure is represented as more graph state

Rejected patch

Planner receives accepted/rejected feedback. It must repair stale, malformed, or unauthorized patches before plain submit.

Agent failure

agent_died, lease release, failure records, and state changes let the scheduler or recovery logic continue without pretending the work passed.

Failed verification/check

Failure evidence is routed to a gap planner or corrective region. Required checks need an explicit failure continuation to avoid silent quiescence.

Lease expiry

Expired leases emit lease_expired, failure records, and failed node state. If the process is still running, the driver can renew with record_heartbeat.

Human authority

Human gates and authority requests block dependent nodes until a decision or authority record is accepted and bound to the waiting input port.

Readbacks

Operators debug the graph through projections and summaries

API surfaces

  • /api/runs/{id}/graph for graph projection and run state;
  • /graph/topology for nodes and edges;
  • /graph/scheduler for ready, blocked, resource-waiting, gate-waiting, and leases;
  • /graph/events for full or summary payloads;
  • /graph/nodes/{node_id} for prompt summaries, controls, records, and callback history;
  • /graph/final-blockers, /graph/patches, /graph/file-state, and /graph/decisions for targeted diagnosis.

Read-model strategy

Heavy payloads such as callbacks, file-state, and output records are summarized. Node detail summaries preserve prompt sections, input ports, bound records, lease metadata, command preconditions, and output records without forcing every UI/API read to replay massive payloads.

Critical invariants

The important rules that keep the graph useful

Runtime invariants

  • graph mutations go through GraphController;
  • side effects are requested through the outbox;
  • leases must be active and generation-matched for callbacks;
  • resource claims prevent unsafe parallel writes;
  • completion is blocked by graph-wide invariants, not by agent confidence.

Prompt invariants

  • planner nodes plan graph structure and do not edit files;
  • workers edit only within their authority packet;
  • verifiers grade every requirement and cite evaluated evidence;
  • checks are deterministic and cannot fabricate pass/fail records;
  • summaries are prompt aids, not correctness authority.

Sources: docs/dynamic-graph/typed-work-graph-requirements.md, graph/contracts.py, graph_runtime/dispatch.py

End-to-end example

A typical dynamic feature run

1Initial plannerReads dynamic feature inputs and creates implementation, validation, gap, and final invariant regions.
2WorkerProduces repository changes, candidate record, and file-state snapshot evidence.
3VerifierConsumes candidate/file evidence and emits per-requirement verdicts.
4Gap/corrective loopFailed evidence routes to gap planner; corrective worker/verifier produces a replacement candidate.
5Final checkHidden or explicit command records pass/fail evidence; final gate decides whether blockers are gone.
The graph keeps expanding only when accepted evidence says new work is needed. If the evidence is good and all invariants pass, the graph quiesces and completes.

What to watch

Operational failure modes that matter

Silent quiescence

A graph with failed evidence but no recovery continuation will stop without useful work. The planner prompt now requires failed checks to route to gap/corrective nodes.

Wrong acceptance region

Control-only regions should contribute control progress, not task acceptance. Fulfillment is contract-driven to avoid treating planner/check-only regions as candidate regions.

Stale patches

Patch base positions protect planners from mutating a graph they no longer observed. Rejected feedback is part of the normal repair loop.

Leaked file changes

Workers operate in run worktrees. Boundary snapshots and main-worktree leak detection protect evidence integrity.

Prompt overload

Prompt text and JSON sections are bounded. Edges can hydrate by summaries or references so the scheduler remains record-authoritative.

Outbox retry

Side effects are at-least-once, so dispatch handlers must be idempotent and recovery must reconcile active leases with real executions.

Sources: docs/dynamic-graph/status.md, workflow/graph_driver.py, graph_runtime/outbox.py

Takeaway

The dynamic graph is a controlled evidence machine

Agents do narrow roles with role-specific prompts. Planners propose graph mutations. The controller validates and records them. Scheduling grants leases deterministically. Evidence is typed, bound, cited, snapshotted, and projected. Completion happens only when the graph proves that the remaining work is gone.
